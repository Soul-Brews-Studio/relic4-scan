# บทที่ 9: ความเป็นส่วนตัว และข้อควรระวัง

transcript ของเอเจนต์คือบันทึกงานจริงของคุณ มีคำสั่งที่พิมพ์ ไฟล์ที่เปิด และบางทีก็มีคีย์ที่เผลอวางลงไป เครื่องมือที่ไล่อ่านทุกไฟล์พวกนี้จึงต้องตอบให้ได้ว่า มันอ่านอะไร เขียนอะไร และส่งอะไรออกไปข้างนอกหรือเปล่า บทนี้ตอบคำถามเหล่านั้นด้วยกฎในโค้ดและของที่เห็นในเดโม แล้วปิดด้วยปัญหาที่ทีมเจอจริงจากเอกสารของ repo

หมายเหตุเรื่องข้อมูล บ้านเดโมของเล่มนี้เป็นของสมมติทั้งหมด สร้างโดย `make-demo-home.py` มี transcript 144 ไฟล์ และมีความลับปลอมอยู่เพียงอันเดียว คือคีย์ `sk-demo-…` ในหนึ่ง prompt เพื่อใช้แสดงหัวข้อ 9.2

## 9.1 อ่านอย่างเดียว ไม่แก้ ไม่เรียกเน็ต

กฎของโค้ดใน AGENTS.md มีสี่ข้อที่เกี่ยวกับความเป็นส่วนตัวโดยตรง หนึ่ง transcript และ vault เป็นอ่านอย่างเดียว สอง relic-scan เขียนเฉพาะในโฟลเดอร์ผลลัพธ์ของตัวเอง คือ `~/.relic-scan` สาม หน้าเว็บไม่เรียกเครือข่ายและไม่โหลด library จากข้างนอก สี่ การเขียนฝั่ง server ต้องมี header `X-Relic`

### ขั้นที่ 1 — ดูก่อนว่าจะอ่านอะไรด้วย --dry-run

ก่อนรันครั้งแรก AGENTS.md ให้ถามเจ้าของเครื่องก่อน เพราะคำสั่ง `run` อ่านทุก transcript ใต้โฟลเดอร์บ้าน ทางที่ปลอดภัยคือรัน `--dry-run` ก่อน มันสแกนแล้วบอกว่าจะอ่านอะไร โดยไม่เขียนอะไรเลย

```bash
relic-scan run --dry-run
```

![กล่อง RELIC SCAN ผล dry run: would read 144 files, new 144, nothing written, ปลายทาง ~/.relic-scan](images/04-dry-run.png)

ภาพนี้ซ้ำจากบทที่ 1 อ่านแล้วเห็นว่า new 144 ส่วน grown, rewritten, unchanged และ gone เป็น 0 หมด เพราะยังไม่เคยทำ index ตัวเลข 0.00 GB คือขนาดที่จะอ่าน ซึ่งเล็กมากในบ้านเดโม

กล่องในภาพมีสองบรรทัดที่เป็นหัวใจ

```
│ dry run · an index would read 144 files, 0.00 GB       │
│ scan 0.2s · nothing written                            │
```

**`nothing written` คือคำยืนยันว่าการดูก่อนไม่แตะดิสก์** ส่วน 144 ไฟล์คือจำนวนที่สแกนเห็นและจะอ่านถ้ารันจริง ปลายทางที่ลูกศรชี้คือ `~/.relic-scan` ที่เดียว

### ขั้นที่ 2 — เมื่อไหร่ที่ข้อมูลออกจากเครื่อง

ข้อมูลออกจากเครื่องได้**สองทางเท่านั้น**ตาม AGENTS.md ทางแรกคือ `relic-scan export --to s3://…` ซึ่งคุณสั่งเอง ทางที่สองคือ `relic-scan ops` กับมุมมอง Activity ที่อ่านสถานะของ hub ด้วย GET หนึ่งครั้ง ตัวแปร `RELIC_OPS_HUB=off` หรือ `--no-hub` ข้ามขั้นนี้ ในบทที่ 8 เราใช้ `--no-hub` ตลอด

นอกจากสองทางนี้ ไม่มีการเรียกเครือข่าย ถ้าอยากพิสูจน์เอง ก็ดูได้ว่าหน้าเว็บให้บริการที่ `127.0.0.1` เท่านั้น ไม่เปิดให้เครื่องอื่น และทาง S3 ก็ไม่เคยเก็บคีย์ไว้ในไฟล์ตั้งค่า (หัวข้อ 7.2)

### ขั้นที่ 3 — ตรวจว่าสำเนาที่ปิดผนึกยังไม่ถูกแตะ

ความเป็นส่วนตัวมีอีกด้านคือความถูกต้อง ข้อมูลที่เปลี่ยนไปโดยไม่มีใครรู้ก็อันตราย `seals --verify` อ่านเดือนที่ปิดซ้ำและเทียบกับผนึก

```bash
relic-scan seals --verify
```

![ผล relic-scan seals --verify ตารางสี่เดือน สามเดือนแรก sealed, matches เดือน 2026-10 เป็น open](images/11-seals-verify.png)

ภาพนี้ซ้ำจากบทที่ 7 ตารางมีสี่เดือน แถวละหนึ่งเดือน ได้แก่ 819, 762, 845 และ 747 แถว เดือนสุดท้ายเป็น `open` เพราะยังไม่ปิด

เดือน 2026-07, 2026-08 และ 2026-09 ขึ้น `sealed, matches` ครบ ภาพนี้เป็นภาพเดียวกับที่ดูในบทที่ 7 แต่ที่นี่ใช้ในมุมต่างออกไป คือเป็นหลักฐานว่าก่อนส่งสำเนาไป S3 ไฟล์ที่ส่งตรงกับที่ปิดไว้ทุกแถว

## 9.2 redact: ความลับถูกแทนด้วยป้าย

ในแถวของ index ที่ข้อความมีคีย์หลุดเข้ามา relic-scan ไม่ทิ้งคีย์ไว้ตามเดิม README บอกสั้น ๆ ว่าขั้นอ่านต่อบรรทัดทำ "redaction" ไว้พร้อม text, thinking และ tools ผลของมันเห็นได้ในคอลัมน์ `red` ของ Parquet

### ขั้นที่ 1 — ถามหาแถวที่ถูก redact

แถวที่ไม่ถูก redact มี `red` เป็น NULL ดังนั้นการกรองด้วย `red is not null` ได้เฉพาะแถวที่มีของลับถูกแทนที่

```bash
duckdb -c "select left(text, 90) as text, red from '*.parquet' \
  where red is not null"
```

![ผล duckdb แถวเดียวที่ red ไม่ว่าง ข้อความมี [openai-key:sk-d…36] และคอลัมน์ red เป็น openai-key](images/19-duck-redacted.png)

ภาพนี้ซ้ำจากบทที่ 6 ตารางมีแถวเดียว ข้อความถูกตัดที่ 90 ตัวอักษร และคีย์ปลอมในนั้นกลายเป็นป้ายแล้ว

ทั้งบ้านเดโมมีแถวเดียวที่ถูก redact ซึ่งเป็น prompt ที่ใส่คีย์ปลอมไว้ ในคอลัมน์ข้อความ คีย์ไม่ปรากฏเต็ม

```
(the key is [openai-key:sk-d…36], do not …   openai-key
```

อ่านได้ว่า **คีย์ถูกแทนด้วยป้ายชนิด `[openai-key:…]`** ในป้ายเหลือแค่ส่วนต้น `sk-d…` กับเลขท้าย 36 เอกสารไม่ได้อธิบายรูปแบบป้ายละเอียดกว่านี้ จึงไม่ตีความเกินภาพ และคอลัมน์ `red` ระบุชนิดว่า `openai-key`

### ขั้นที่ 2 — อ่านผลอย่างระวัง

การ redact ช่วยให้ index ไม่ถือคีย์เต็มไว้ แต่มันเป็นการแทนที่ในแถวของ index เท่านั้น **ไฟล์ transcript ต้นฉบับไม่ถูกแก้** เพราะกฎ "อ่านอย่างเดียว" ดังนั้นคีย์เต็มยังอยู่ใน `.jsonl` ของเอเจนต์ตามเดิม ถ้าคีย์หลุดเข้าไปจริง ต้องหมุนคีย์ที่ต้นทาง ไม่ใช่หวังว่า index จะแก้ให้

AGENTS.md ยังเตือนอีกข้อสำหรับทุกคนที่ถาม index ว่า transcript เก็บงานส่วนตัว ให้อ่านเฉพาะสิ่งที่เจ้าของขอให้หา และไม่คัดลอกแถวออกจากเครื่อง

## 9.3 สำเนาซ้ำถูกพับเป็นแถวเดียว

เครื่องหนึ่งมักมี transcript ชุดเดียวกันหลายที่ เช่น mirror จากเครื่องอื่น ที่เก็บถาวร หรือสำรอง ถ้าแต่ละสำเนานับเป็นแถวแยก ตัวเลขทุกตัวจะเพี้ยนไปหมด และข้อความเดียวกันถูกอ่านซ้ำหลายรอบ

AGENTS.md อธิบายว่า **สำเนาของ transcript ในหลาย home ถูกพับเป็นแถวเดียว** แม้สำเนาจะต่างกันที่ metadata เช่น cwd ที่บันทึก คอลัมน์ `sources` ของแถวนั้นบอกทุกสำเนาที่พบ ในรูป `agent:path:line` จึงรู้ได้ว่าแถวหนึ่งมาจากไหนบ้าง

### ขั้นที่ 1 — เห็นผลของการพับในตัวเลข

**ตัวเลขไม่ถูกนับซ้ำ** ผลในเดโมคือบนหน้า Tree และ Paths ตัวเลขที่เห็นคือ 145 ไฟล์ 144 sessions กับ 3,173 แถว โดยไม่มีการนับซ้ำ เพราะเดโมไม่มี mirror จริง ผลของการพับเลยไม่เด่นในภาพ บทนี้ไม่แต่งตัวเลขการพับขึ้นมา

อีกชั้นหนึ่งคือ ledger ที่บทก่อนเล่าไว้ AGENTS.md ระบุว่าสำเนาที่ ledger จำได้จะไม่ถูกอ่านซ้ำ และถูกจดไว้ใน `_state.tsv` (คอลัมน์ `copy_of`) กับ `_ledger.tsv` แทนที่จะอยู่ใน `sources` ของแถว ถ้าอยากให้เห็นว่า relic-scan ข้ามอะไรไปบ้าง ใช้ `relic-scan log` ซึ่งนับ `copies`, `resumed` และ `past_changed` พร้อมรายการไฟล์ทีละไฟล์

### ขั้นที่ 2 — มองจากมุมความเป็นส่วนตัว

การพับช่วยสองเรื่อง หนึ่ง ข้อความส่วนตัวชิ้นเดียวไม่ถูกเพิ่มเป็นหลายแถวใน index เมื่อก๊อปอยู่หลายที่ สอง คุณรู้ว่าแถวนั้นมีรอยอยู่ที่ไหนบ้างจาก `sources` ถ้าต้องไปจัดการ เช่นลบสำเนาเก่า ต้องรู้ว่ามีสำเนาที่ไหน

แต่ข้อควรระวังคือ การลบแถวออกจาก index ไม่ลบไฟล์ต้นฉบับ และการลบไฟล์ต้นฉบับก็ไม่ได้ลบแถวใน index ทันที ที่มาของเรื่องนี้อยู่ที่หัวข้อต่อไป

## 9.4 ปัญหาที่ทีมเจอจริง และทางแก้

หัวข้อนี้รวมเฉพาะข้อควรระวังที่เขียนไว้ในเอกสารของ repo เอง ไม่มีข้อไหนมาจากการเดาของผู้เขียนเล่ม ทุกข้อบอกที่มา เรียงตามโอกาสที่คุณจะเจอ

### ขั้นที่ 1 — เดือนที่ปิดแล้วต่างจากใน store

ที่มา AGENTS.md ส่วน "Copy the sealed months" และ scripts/README.md อาการคือ เดือนที่ปิดไปแล้วถูกปิดใหม่หลังมีแถวช้ามาถึง สำเนาใน S3 จึงต่างจากไฟล์ในเครื่อง

```
A sealed month that differs in the store (it was sealed again after
a late row) is refused unless --overwrite.
```

บล็อกข้างบนคัดจาก AGENTS.md ตามตัวอักษร และไม่ได้รันในเดโม **ทางแก้คือรัน export ด้วย `--overwrite` ด้วยมือ** หลังตรวจแล้วว่าต้องการจริง งานสำรองตอนกลางคืนไม่ทับให้เอง

### ขั้นที่ 2 — index เก่ามีรูปร่างไม่เหมือนเวอร์ชันปัจจุบัน

ที่มา AGENTS.md ส่วน "Query the index" อาการคือ คอลัมน์ `model`, `msg_id`, `out_tokens` เป็น NULL ใน index ที่เขียนด้วยเวอร์ชัน v26.10.23-alpha.1858 หรือเก่ากว่า และเดือนที่เขียนก่อนมีคอลัมน์ `in_tokens`, `cache_read`, `cache_write` ก็อ่านเป็น NULL เช่นกัน ส่วน `meta/sessions.parquet` ก็ไม่มี `cwd`, `title`, `branch` หรือ `version` จนกว่าจะอ่านไฟล์ใหม่

ทางแก้ที่เอกสารให้: **ทำ index ใหม่ตั้งแต่ต้น** คือย้าย `~/.relic-scan` ออกไปข้าง ๆ แล้วรัน `relic-scan run` ใหม่

```
move ~/.relic-scan aside, then relic-scan run
```

### ขั้นที่ 3 — index ใหม่ทิ้งแถวของไฟล์ที่หายไป

ที่มา docs/TALK.md ส่วน "Who fixes what" อาการคือ index ใหม่ตั้งแต่ต้น**จะทิ้งแถวที่ไฟล์ต้นทางหายไปแล้ว** ดังนั้นถ้าคุณเคยลบหรือย้าย transcript เก่า ตัวเลขหลังทำใหม่อาจน้อยลง ทางแก้ที่เอกสารระบุคือ เทียบจำนวนแถวก่อนสลับไป index ใหม่ เก็บของเก่าไว้ข้าง ๆ จนแน่ใจ

### ขั้นที่ 4 — รันบางช่วงเวลาแล้วหยุด หรือรันชนกัน

ที่มา docs/TUTORIAL.md ท้ายเล่ม ตารางเมื่อมีอะไรผิด สองข้อ ข้อแรก ถ้า run หยุดเพราะมีตัวอื่นถือ lock ซึ่งหมายความว่า **หนึ่ง writer ต่อหนึ่งโฟลเดอร์** ให้รอตัวนั้นเสร็จ ข้อสอง ถ้า run แบบช่วงหยุดด้วยข้อความ "indexed without one" แปลว่า `--month` และธงวันที่อื่น ๆ เขียนลงโฟลเดอร์ของตัวเอง ไม่ต้องตั้ง `--out`

ถ้าไฟล์ที่เจอน้อยกว่าที่คิด ตารางนั้นแนะนำให้เช็ก root ที่สแกน (ธง `--root` หรือหน้า Settings) และรัน `relic-scan log --diff 0`

### ขั้นที่ 5 — เปลี่ยน binary ที่กำลังรันอยู่

ที่มา scripts/README.md และ docs/TALK.md อาการคือ บน macOS ถ้า `cp` ทับ binary ที่กำลังรันอยู่ ระบบจะฆ่าโปรเซสนั้น ทางแก้ที่เขียนไว้คือ **ลบก่อนด้วย `rm -f` แล้วค่อย `cp`**

```
rm -f ~/.local/bin/relic-scan && cp target/release/relic-scan ~/.local/bin/
```

บรรทัดข้างบนเป็นการเรียบเรียงตามคำแนะนำ ไม่ได้รันในเดโม เส้นทางปลายทาง `~/.local/bin/relic-scan` มาจากที่ install.sh ติดตั้ง TALK.md เตือนเพิ่มอีกชั้น ให้ทำหลัง build ตัวใหม่เสร็จแล้วเท่านั้น เพราะเคยมีครั้งที่ `cp` ล้มหลัง `rm` แล้ว relic-scan หายไปหกนาทีบนเครื่อง white

ครบทั้งเก้าบทของการใช้งาน การอ่าน index และการเดินข้อมูล ส่วนภาคผนวกต่อจากนี้ลงไปในรูปแบบของ transcript ที่ relic-scan อ่านจริง บรรทัดต่อบรรทัด
